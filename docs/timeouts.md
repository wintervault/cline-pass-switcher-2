# 长请求超时：大上下文的非流式请求为什么会失败

> 2026-10-17 实测记录。触发问题：用户报告「订阅模型里勾上渠道后实际用不了 / 开始对话就报错」。
> 本文是排查结论与修复选项；实施情况见 CHANGELOG。

## 一、现象（两个不同的问题，别混在一起）

1. **planner 模型**（`cline-pass/deepseek-v4.1-flash`）：勾上 `deepseek`「不管用，但还能用」。
   这是**参数被网关丢弃**（账号风控），不是本项目的 bug——见 `docs/pinning.md`。
   能用的原因是网关自己把 deepseek 排在执行链首位，与勾选无关。
2. **direct 模型**（`cline-pass/mimo-v2.6-pro`）：勾上 `xiaomi` 后，测试台能用、探测/校验都通过，
   但**实际请求频繁报错**；不勾选就不报错。共同形态：**开始对话时报错，对话中正常**。

## 二、本机数据（只读线上 500 条历史）

配置现状：三个模型都是 `pinMode: strict` + 单渠道（deepseek / xiaomi / z-ai）。

mimo 的请求分成两组，界限泾渭分明：

| 请求形态 | 条数 | 结果 |
|---|---|---|
| 流式（stream=true） | 88 | **全部成功**，provider=xiaomi，5–15s |
| 非流式（stream=false） | 5 | **全部失败**：`attempt timeout (60000ms)` ×2、`attempt timeout (~30s)` ×2、`no upstream attempt was made` ×1 |

- 失败集中在 11:34–11:38、17:37–17:38，不是持续性的
- 17:37/17:38 两条的 `attempts=[xiaomi,xiaomi]`：第一次 60s 超时、重试吃掉剩余 30s，
  **90s 预算烧光** → 502
- `no upstream attempt was made` 是**客户端在发出请求前就断开**（链一次都没发），
  属于取消，不是上游错误（`proxy/chain.ts` 的收尾分支）

## 三、隔离实测（dev 实例：端口 3133、临时数据目录、复制线上配置）

| 变体 | 结果 |
|---|---|
| 小请求 · 非流式 · 无 tools | 200 / 7s |
| 小请求 · 非流式 · 带 tools | 200 / 9s |
| 4.5 万 token · 非流式 | 200 / 26s |
| 4.5 万 token · 非流式 · 带 tools | 200 / 8s |
| 4.5 万 token · 流式 · 带 tools | 200 / 6s |
| **10 万 token · 流式** | **200 / 13s** |
| **10 万 token · 非流式** | **502 / 91s（attempts=2，第二次 `attempt timeout (29987ms)`）** |

**同一上游、同一份负载：非流式比流式慢 5 倍以上。** 大上下文下非流式越过 60s 单次超时，
重试再吃掉剩余预算 → 必然 502。这与线上失败记录的签名完全一致。

顺带解释了「测试台能用、校验也通过」：它们发的都是**小请求**。
校验/探测的成功只能证明「小请求可用」，不能代表真实大请求可用。

## 四、根因：2.0.0 把超时收紧了（不是「原版能用」的错觉）

| 参数 | 原版（上游 1.x） | 现在（2.0.0 起） |
|---|---|---|
| `failover.attemptTimeoutMs` | **120s** | **60s** |
| `failover.budgetMs`（全局预算） | 无 | **90s** |

两者叠加：单次最长 60s、总和最长 90s。**非流式大请求（>60s）从「慢但能成」变成「必然失败」**——
这正是用户记忆里「原版可以」的来源。2.0.0 收紧的初衷是 agent 场景别久挂，但没考虑到
「非流式 + 大上下文」这种慢路径。

## 五、为什么「对话开始时报错、对话中正常」

- 对话中的主请求是**流式**（实测 13s 级）→ 正常
- 对话开始时的工具调用/标题/摘要类请求是**非流式**（客户端行为）→ 走慢路径 → 失败

同一个机制也解释了「有时候别的模型也有这种情况」：不限于 mimo，任何**勾选的渠道在
非流式路径上偏慢**的模型都会这样。

## 六、修复选项（未实施）

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐）非流式内部改走流式** | 客户端发 `stream:false` 时，向上游用流式请求、本地累积成完整 JSON 返回。同一负载 13s vs >60s，且不依赖具体 provider | 要组装 SSE 的 content / tool_calls / finish_reason；`proxy/stream.ts` 已有增量解析可复用 |
| B 放宽/分级超时 | 非流式放宽（如 attempt 120s、budget 180s），流式保持短超时（首字节慢就该切） | 真挂了的请求会多等；回到原版行为 |
| C 渠道耗时可见 | Playground 路由面板的「最近耗时」列目前恒为「—」，填上后能看出哪个渠道慢 | 纯前端 |
| D 过滤取消噪声 | `no upstream attempt was made` 是客户端断开，不该记成错误/红标 | 小 |

## 七、边界

- 「非流式慢」是否 xiaomi 独有：未验证（换 deepinfra 那条撞了 429）。方案 A 不依赖这个结论。
- 校验/探测用小请求探不到这个问题——如果采用方案 A，校验也应覆盖「大请求」形态（可选）。
